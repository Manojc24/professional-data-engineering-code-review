## Project Overview

This repository demonstrates an end-to-end code-review workflow for a Python/Pandas sales ETL pipeline. It compares an initial unreviewed implementation against a modular, refactored version built for data reliability and maintainability.

The repository includes:
- **Initial Implementation**: [`junior_code/smartphone_pipeline.py`](junior_code/smartphone_pipeline.py) — Initial pipeline implementation containing common correctness, performance, and data handling flaws.
- **Code Review Findings**: [`reports/code_review.md`](reports/code_review.md) — Technical audit documenting 18 identified issues across correctness, reliability, performance, and maintainability.
- **Refactored Implementation**: [`reviewed_code/smartphone_pipeline.py`](reviewed_code/smartphone_pipeline.py) — Modular, vectorised pipeline with defensive validation, structured logging, and robust error handling.
- **Test Suite**: [`tests/test_smartphone_pipeline.py`](tests/test_smartphone_pipeline.py) — Comprehensive pytest suite validating pipeline transformations, edge cases, and KPI calculations.

## Business Scenario

The pipeline automates the daily processing of smartphone transaction logs exported from an order management system to support reporting and analytics for business intelligence teams.

Key pipeline responsibilities:
- **Ingestion & Validation**: Read daily order exports and validate schema and data types.
- **Data Quality & Cleaning**: Deduplicate records, normalize text formatting (brand and country names), resolve mixed date/boolean representations, and filter domain range anomalies (invalid prices, quantities, and ratings).
- **Transformation & Analytics**: Derive transaction metrics including net revenue (factoring in discounts), return rates on valid entries, average order values, and brand performance rankings.
- **Reporting & Export**: Generate visualization charts for weekly business reviews and export cleaned datasets in both Parquet and CSV formats for downstream analytics.

## Pipeline Architecture

```
Raw CSV → load_data() → validate_raw() → clean_data() → add_derived_columns()
        → compute_kpis() → generate_charts() → save_processed()
```

| Stage | Function | Description |
|---|---|---|
| Load | `load_data()` | Read CSV, fail fast if file or schema is wrong |
| Validate | `validate_raw()` | Log data quality counts before any rows are dropped |
| Clean | `clean_data()` | Dedup, null handling, normalisation, range filtering |
| Transform | `add_derived_columns()` | Add revenue, discount_amount, year_month |
| Analytics | `compute_kpis()` | Total revenue, return rate, AOV, unique counts |
| Charts | `generate_charts()` | 4 charts saved to reports/charts/ |
| Output | `save_processed()` | Write CSV and Parquet to data/processed/ |

## Data Quality Issues

The raw data contains the following intentional problems (all resolved by `clean_data()`):

- **~80 exact duplicate rows** — simulates a double-export from the upstream system
- **~3.5% null values per column** — injected across selected columns at random
- **Inconsistent country names:** `"india"`, `"INDIA"`, `"Inda"`, `"india "` (trailing space)
- **Inconsistent brand casing:** `"apple"`, `"APPLE"`, `"Samsung"`, `"SAMSUNG"`
- **Invalid prices:** negative values, zero, values above the plausible ceiling
- **Invalid quantities:** zero or negative
- **Invalid ratings:** values below 1.0 or above 5.0
- **Mixed returned formats:** `True`, `"yes"`, `"1"`, `1`, `"True"`, `NaN`
- **Mixed date formats:** `YYYY-MM-DD`, `MM/DD/YYYY`, `DD-MM-YYYY`, literal `"N/A"`

## Code Review Approach

Reviews are prioritised by impact on correctness and reliability:

1. **Correctness** — bugs that produce wrong results (revenue, return rate)
2. **Reliability** — code that crashes or silently corrupts data
3. **Performance** — operations that will not scale
4. **Maintainability** — naming, structure, documentation
5. **Style** — PEP 8, consistency

Severity levels: `CRITICAL` · `HIGH` · `MEDIUM` · `LOW`

Full review: [`reports/code_review.md`](reports/code_review.md)

## Key Issues Identified

18 issues total — 5 critical, 4 high, 5 medium, 4 low.

### Critical

| ID | Issue | Impact |
|---|---|---|
| C1 | Revenue ignores discount (`price × qty` instead of `price × (1−discount) × qty`) | Every revenue figure overstated by approximately the average discount rate |
| C2 | Return rate denominator includes NaN rows (`len(df)` instead of valid-only count) | Return rate understated whenever `returned` is null for some orders |
| C3 | `dropna()` on the full DataFrame | Drops any row missing any column — removes ~30% of otherwise valid data |
| C4 | `pd.to_datetime()` without `errors='coerce'` | Crashes on the first malformed date string |
| C5 | `iterrows()` loop assigns scalar to entire column | Every row gets the last row's `discount_amount` |

### High

| ID | Issue |
|---|---|
| H1 | Hard-coded absolute path (`C:/Users/junior_dev/Desktop/...`) — breaks on any other machine |
| H2 | Chained assignment `df['brand'][i] = ...` — may silently not update the DataFrame |
| H3 | Same chained assignment pattern on the `returned` column |
| H4 | No input validation — silent failure if the CSV is missing or schema changes |

### Medium

| ID | Issue |
|---|---|
| M1 | `iterrows()` for brand normalisation — avoidable with `.str.strip().str.title()` |
| M2 | `iterrows()` for returned mapping — avoidable with `.map()` |
| M3 | `apply(lambda x: int(x))` — `astype()` / `pd.to_numeric()` is the idiomatic replacement |
| M4 | `rating > 0` filter keeps ratings 0.1–0.9; should be `>= 1.0` |
| M5 | Charts saved to working directory with no path — pollutes wherever the script runs from |

### Low

| ID | Issue |
|---|---|
| L1 | Variable names `df2`, `top2`, `ctry2`, `x`, `val` — no semantic meaning |
| L2 | Zero docstrings on any function |
| L3 | PEP 8 violations throughout (spacing, line length) |
| L4 | Country normalisation logic duplicated inside `main()` |

## Refactoring Approach

**Correctness fixes**
- Revenue: `price × (1 − discount) × quantity`
- Return rate: `valid.sum() / len(valid)` where `valid = df["returned"].dropna()`
- `dropna(subset=critical_cols)` — only drop rows missing fields required for KPI calculation
- `pd.to_datetime(..., errors="coerce", format="mixed")` — handles multiple date formats, converts bad dates to NaT
- Vectorised `discount_amount` computation — one multiply, no loop

**Performance**
- All three `iterrows()` loops replaced with `.str` methods and `.map()`
- `apply(lambda x: int(x))` replaced with `pd.to_numeric().astype("Int64")`

Both approaches execute in compiled C/NumPy code rather than pure Python row iteration.
The absolute difference is small on 5,000 rows, but the pattern matters at scale.

**Reliability and maintainability**
- Relative paths computed from `__file__` — portable across machines
- Schema validation at load time with clear error messages
- Named constants (`MIN_RATING`, `MAX_VALID_PRICE`, `COUNTRY_ALIASES`) instead of magic numbers
- `logging` module instead of `print()` — output level is configurable
- Charts saved to `reports/charts/` — predictable location regardless of working directory
- Each pipeline stage is a separate testable function
- `df.copy()` at the start of transformation functions — callers' DataFrames are not mutated
- Type hints and docstrings on all public functions

## Testing

**Framework:** pytest  
**File:** `tests/test_smartphone_pipeline.py`  
**Result:** 57 tests, all passing

Tests are written against individual pipeline functions using minimal DataFrames
constructed for each scenario. The full 5,000-row dataset is not used in tests —
this keeps each test fast and failure messages specific.

| Area | Tests |
|---|---|
| Ingestion (file not found, schema validation) | 3 |
| Duplicate removal | 1 |
| Critical vs optional null handling | 4 |
| Price, quantity, rating range validation | 8 |
| Revenue formula — correct and regression guard | 3 |
| Return rate — NaN exclusion and edge case | 2 |
| Brand normalisation (parametrised) | 7 |
| Country alias resolution (parametrised) | 10 |
| Returned column mapping (parametrised) | 15 |
| Date parsing robustness | 1 |
| Derived columns present | 1 |
| Aggregation correctness | 2 |

The revenue and return-rate tests include explicit regression guards: they assert
the wrong formula produces a different result, so the fix cannot silently revert.

## How to Run

**Requirements:** Python 3.11+

```bash
# Clone and install dependencies
git clone <repo-url>
cd professional-data-engineering-code-review
python -m venv .venv
source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt

# Generate the dataset (required once)
python generate_dataset.py

# Run the reviewed pipeline
python reviewed_code/smartphone_pipeline.py

# Run the tests
pytest tests/ -v

# Run tests with coverage
pytest tests/ -v --cov=reviewed_code --cov-report=term-missing
```

**Pipeline output:**
- `data/processed/clean_smartphone_sales.csv`
- `data/processed/clean_smartphone_sales.parquet`
- `reports/charts/brand_revenue.png`
- `reports/charts/monthly_revenue.png`

- `reports/charts/country_revenue.png`
